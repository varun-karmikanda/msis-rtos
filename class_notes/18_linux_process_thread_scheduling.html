Linux process vs thread scheduling

A walkthrough: process/thread structure, how the scheduler treats them, and how cgroups change the picture on a 4-core system.

1. Process vs thread — internal structure

Linux doesn't have a separate "thread" data structure. Both processes and threads are represented by the same kernel object — task_struct — and both are created by the same syscall, clone(). The difference is entirely about which resources you tell clone() to share.

Threads: shared address space, private stack + registers

Implementation notes:

  • fork() = clone(SIGCHLD) with none of the sharing flags — everything is copy-on-write duplicated.
  • pthread_create() = clone() with CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD | .... CLONE_THREAD puts the new task in the same thread group (tgid), so getpid() is shared while gettid() differs per thread.
  • The scheduler is oblivious to the process/thread distinction — it just special-cases "same mm" to skip the switch_mm() TLB reload.
  • On an RTOS (FreeRTOS, uC/OS-III) a "task" is exactly what a Linux thread is — a stack + register context sharing one flat memory map, because there's no MMU-backed isolation to opt out of.

2. Scheduling 3 processes + a 4th, 3-threaded process

The scheduler doesn't see "processes" — it sees a runqueue of task_structs. A multithreaded process simply contributes more entities to that queue.

CFS orders the runqueue by vruntime (accumulated CPU time) and always dispatches whoever's behind, weighted by nice — the round-robin picture above is an intuitive approximation of that. Because P4's 3 threads are 3 separate task_structs with 3 separate vruntime counters, they compete individually against P1–P3, giving P4 roughly 3x the CPU attention of a single-threaded process — unless it's placed in a cgroup, which is exactly what changes in the next section.

5. Correcting the scale: cgroup total vs individual threads

A cgroup doesn't shrink each thread's individual slot — it caps the combined total of all its threads. Drawn to scale by total runtime (P1=4, P2=3, P3=2, P4: T1=2/T2=3/T3=4, P5: T1=2/T2=3/T3=2):

P4's three bars are separate rows because each competes independently against P1–P3 for turns — nothing stops P4 from accumulating 9 total slots. P5's bar is one continuous shape because that's the real constraint surface: whatever cpu.shares/cpu.weight or cpu.max is set applies to the outer pink bar's length, and the 2/3/2 split inside it is internal bookkeeping among its three threads, invisible outside the cgroup.
