three-thread-blink: the address space at runtime

Everything the chip is doing while three LEDs blink, laid out by address - from the vector table at the bottom of flash to the three task stacks tucked inside a 4 KB heap arena in RAM.

flash - code & constants, never changes at runtime RAM - everything that changes while running peripheral registers core (ARM-defined, not ST) registers

The whole space, at a glance

A Cortex-M3 has one flat 4 GB address space - no MMU, no separate views per task. Everything this project touches falls into four narrow bands of it; the rest is simply never addressed.

Flash - 0x0800_0000 to 0x0800_FFFF (64 KB)

Everything here was true before power was ever applied, and stays true for the life of the program - it's the ELF's .isr_vector, .text, and .rodata, written once at flash time.

RAM - 0x2000_0000 to 0x2000_4FFF (20 KB)

Everything here is only true right now. This is where the three tasks, their stacks, and the scheduler's own bookkeeping actually live while the program runs.

Two stacks, two purposes. _estack at the very top of RAM is the Main Stack Pointer - it's what SysTick_Handler and PendSV_Handler run on, in Handler mode, no matter which task was interrupted. Each task's own stack, down in the heap arena, is addressed through the Process Stack Pointer instead - swapped by PendSV_Handler at every context switch. The two never collide because the CPU is always in exactly one mode at a time.

Peripheral & core registers

The only addresses in this whole program that aren't memory in the usual sense - reads and writes here reach real silicon (clock gates, pin drivers, a hardware countdown timer), not storage.
